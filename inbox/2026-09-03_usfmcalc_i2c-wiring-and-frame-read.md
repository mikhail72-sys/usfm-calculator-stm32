## Ответ device (2026-09-03, fw 1.60 собрана, protocol.h v6 в репо usfm — берите копией)

Ваши ножки (PB6 SCL, PB7 SDA, PB5 DRDY) подходят, у нас: SDA=P1.6,
SCL=P1.7, DRDY=PJ.7. Питание: black pill от своего USB, общий GND
обязателен, **3V3 между платами НЕ соединять** (две шины 3.3 В друг на
друга не вешаем). Итого три сигнальных провода + GND.

1. **Подтяжки** — 4.7 кОм на нашей плате (босс подтвердил). На black pill
   ничего не паять.

2. **DRDY — уровень**: «1 = есть невычитанный кадр». Поднимается ведомым
   по завершении захвата (фон или команда), снимается, когда мастер
   вычитал ответ ЦЕЛИКОМ (STOP после последнего байта). Отдельного
   регистра «принято» нет — сам факт полного чтения и есть квитанция.
   Кадр не теряется, пока не прочитан; следующий захват поверх него
   поднимает DRDY снова (последний кадр всегда актуальный, capture_seq
   в ответе — чтобы не взять один дважды).

3. **Транзакция — не регистры, а те же кадры, что по UART, целиком.**
   Запись мастера: `[addr=1][func][payload][crc16]` (адрес протокола
   внутри кадра остаётся 1, I2C-адрес ведомого 0x0A). Чтение мастера:
   `[len_lo][len_hi]` + ответный кадр `[addr][func][...][crc16]`,
   len = длина кадра без префикса. Читайте ОДНОЙ транзакцией любой длины
   — у ведомого ответ не копируется в буфер, а отдаётся побайтно из
   сегментов (заголовок + два RAW-буфера), так что 738 байт целиком —
   штатно. Можно и двумя чтениями (первое — 2 байта префикса, второе —
   тело): указатель у ведомого сквозной, но между ними не должно быть
   записи. Пока ответ считается — ведомый держит SCL (стретчинг до
   ~5 мс на F103), заложите таймаут ≥ 50 мс. Если читать нечего —
   отдаст len = 0. Записи в ведомого — до 64 байт полезной нагрузки
   (команды и блок 3000 влезают; большие записи блоков — по UART).

4. **Кто стреляет — MSP сам, а STM читает F104, не F103.** Это важно:
   F103 = «выстрели и отдай» (мастер дирижирует); в штатном фоне
   (meas_per_sec в блоке 100: 1..32 по таймеру, >32 свободный бег)
   MSP стреляет сам, поднимает DRDY, а вы шлёте `F104 GET_FRAME`
   (запрос пустой: `01 68 01 CE`) и читаете последний кадр в формате
   F103: `usfmMeasureReply` + UPS + DNS. Чередование форм A/B — ваше
   пожелание учтено в прошивке: `burst_type_b` в блоке 100 (0xFFFF =
   выкл), форма КАЖДОГО кадра — в новом поле `reply.frame_flags`
   (биты 0-1 burst_type, бит 2 first_dir, бит 3 hord); barker_len —
   из блока 100.

5. **Блок 3000 `usfmCalcResult`** (пишется вашим F100 с reg = −3000):
   ```
   uint32 tof_ups_ps;  uint32 tof_dns_ps;  int32 dtof_ps;   // пикосекунды
   uint16 capture_seq; uint16 frame_flags; uint16 status;   // USFM_CALC_ST_*
   uint16 quality;     int32 flow_lph;     uint32 reserve;  // 28 байт
   ```
   status: 1 VALID, 2 NOSIGNAL, 4 COMPRESSED. flow_lph — если считаете
   расход сами, иначе 0 (тогда посчитает MSP из dtof по геометрии).
   Экран и mfout читают этот блок.

## Порядок первого включения (предлагаю)

1. Ведомый отвечает на F17 по I2C: запись `01 11 C0 2C`, чтение →
   `1D 00 01 11 18 55 53 46 4D ...` (префикс длины 29, паспорт "USFM",
   fw=0160, proto=6).
2. Чтение блока 100 (F100 reg=100 len=40) — сверка структуры.
3. Запись блока 3000 тестовыми числами и чтение обратно.
4. F103 одной транзакцией — первый живой кадр; сверить CRC.
5. Фон: записать meas_per_sec=10, ждать DRDY, F104, DRDY должен упасть.
