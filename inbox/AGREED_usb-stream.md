# AGREED: USB-поток кадров от вычислителя STM32 к PC, версия 1 (ЧЕРНОВИК)

**Предложено:** 2026-09-03, usfmcalc
**Статус:** proposed — ждёт cheater (приёмник) и analyzer (потребитель
кадров в базе); молчание до 2026-09-10 = принято.
**Правка этого файла:** любой стороной, с датой и автором.
**Канонические структуры:** `C:\Piezus\TI\usfm\protocol.h` (usfmMeasureReply,
блок результатов вычислителя — когда device его добавит). Заголовок потока
`usfmStreamHdr` живёт в `usfmcalcv0/stream.h` (появится на этапе 1) и
предлагается к переносу в protocol.h при следующем proto_ver++.

## Транспорт

USB CDC-ACM (виртуальный COM), VID:PID 0483:5740, параметры линии
(бод/биты) не имеют значения. Полный дуплекс: поток STM→PC идёт
непрерывно, пока включён; команды PC→STM — отдельный канал (ниже).
Границы кадров USB **не** переносят границы записей: приёмник должен
собирать записи по заголовку и длине, ресинхронизация — по магику + CRC.

## Запись потока (STM32 → PC)

```
[usfmStreamHdr][usfmMeasureReply][UPS int16*n][DNS int16*n][result][crc16]
```

- `n = usfmMeasureReply.sample_size` (как в F103: при BADPARAM n = 0);
- `result` — блок «результаты вычислителя» длиной `hdr.result_len`
  (0 на этапе 1 — транзит без математики; структура — в protocol.h от
  device);
- `crc16` — CRC16 Modbus (полином 0xA001, старт 0xFFFF) по всем байтам
  записи от первого байта заголовка до конца `result`, little-endian;
- всё little-endian, структуры без дырок выравнивания.

```c
typedef struct
{
    uint32_t    magic;          // 0x4D465355 = "USFM" в порядке байт
    uint16_t    hdr_ver;        // = 1
    uint16_t    hdr_len;        // = sizeof(usfmStreamHdr) = 24
    uint32_t    seq;            // счётчик записей потока STM32 (с 0 при
                                //   включении потока); дырка = потеря
    uint32_t    tick_ms;        // SysTick STM32 в момент приёма кадра, мс
                                //   (ТОЛЬКО для темпа/диагностики: время
                                //   пролёта живёт в домене MSP430)
    uint16_t    frame_len;      // байт после заголовка до crc:
                                //   sizeof(reply) + 4*n + result_len
    uint16_t    result_len;     // длина блока результата (0 = нет)
    uint16_t    flags;          // USFM_STREAM_F_*
    uint16_t    err_i2c;        // накопительный счётчик ошибок I2C
                                //   (таймаут/NACK/CRC) с включения
} usfmStreamHdr;                // 24 байта

#define USFM_STREAM_MAGIC       (0x4D465355UL)
#define USFM_STREAM_HDR_VER     (1)
#define USFM_STREAM_F_SYNTH     (0x0001)  // кадр синтетический (имитатор
                                          //   STM32, не с MSP430)
#define USFM_STREAM_F_DROPPED   (0x0002)  // перед этой записью были
                                          //   сброшены кадры (USB не
                                          //   успевал); сколько — по seq
#define USFM_STREAM_F_I2C_ERR   (0x0004)  // при чтении этого кадра были
                                          //   повторы I2C (кадр целый)
#define USFM_STREAM_F_CALC      (0x0008)  // result заполнен вычислителем
```

Размер записи для кадра v1 (n = 176): 24 + 14 + 704 + 0 + 2 = 744 байта.
При 65 кадр/с — 48 КБ/с.

Форма кадра (burst_type, barker_len, first_dir) — из `usfmMeasureReply` /
снимка блока 100; когда MSP чередует формы в серии, приёмник различает их
по этим полям записи, ничего дополнительного в заголовке нет.

## Команды PC → STM32 (черновик, обсуждаемо)

Предлагаю тот же кадр, что у прибора, но с длиной вместо тишины (на USB
тишины нет):

```
[len16 LE][addr][func][payload...][crc_lo][crc_hi]
```

- `len16` — байт от addr до crc включительно;
- `addr` вычислителя = **2** (прибор = 1); на 0xFF тоже отвечает;
- F17 SLAVE_ID — паспорт вычислителя (`usfmInfo`, name = "USFMCALC");
- F100 SERVICE — карта регистров вычислителя (своя, база 3000+: поток
  вкл/выкл, темп имитатора, режим счёта, счётчики) — структуры объявлю
  в `stream.h`, в protocol.h переедут вместе с заголовком;
- ответы — тем же кадром с len16, идут в том же USB-потоке, что и
  записи; приёмник различает по первому байту: записи начинаются с
  магика "USFM" (0x55), кадр-ответ начинается с len16, чей старший байт
  для ответов ≤ 255 байт равен 0x00. Если это неудобно читеру — ответы
  можно заворачивать в запись потока с отдельным magic; скажите.
